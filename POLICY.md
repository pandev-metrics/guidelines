# Git Flow Policy

Краткая политика для команды. Можно положить в корень репозитория или в wiki.

## Ветки

1. Работа над задачей — только в ветке `feature/<KEY>`, `bugfix/<KEY>` или `hotfix/<KEY>`.
2. `<KEY>` — ключ из трекера: `PROJ-123` (латиница, дефис, цифры). Без хвоста после номера.
3. Интеграция — через merge request / pull request в `dev` (или вашу базовую ветку).
4. Прямые коммиты в `dev` / `prod` / `main` запрещены (защитите ветки на сервере).

Примеры:

- ✅ `feature/PROJ-42`
- ✅ `bugfix/PROJ-42`
- ❌ `feature/PROJ-42-login`
- ❌ `feature/login`
- ❌ `PROJ-42`

## Коммиты

Формат первой строки:

```text
feature/PROJ-42 - Краткое описание изменения
```

Тот же тип и ключ, что в имени ветки (или допустимый тип из списка), затем пробел, дефис, пробел, subject.

Допустимые типы: `feature`, `bugfix`, `hotfix`, `fix`, `refactor`, `docs`, `test`, `chore`, `ci`, `style`, `release`.

Исключения: сообщения `Merge …` и `Revert …`. Для `fixup!` / `squash!` / `amend!` проверяется исходный subject после префикса.

## Merge requests

- Целевая ветка: `dev` (или согласованная интеграционная).
- MR сразу ready for review; draft — только по явной договорённости.
- В `prod` / `main` — только из принятого потока окружений, не из feature-ветки напрямую (если у вас иначе — зафиксируйте явно).

## Люди и агенты

Правила одинаковы. Локальные хуки (`.githooks` или husky) и server `pre-receive` не дают запушить обход. Агентам читают `AGENTS.md` и `.cursor/rules/git-flow.mdc`.
