# Git Flow Policy

Краткая политика для команды. Можно положить в корень репозитория или в wiki.

## Ветки

1. **Ветку с ключом задачи заводят до начала работы**, до первой правки файлов. Время из IDE и AI-токены записываются с именем текущей ветки: работа на ветке без ключа к задаче не попадёт, даже если ветку потом переименовать.
2. Ветка — `feature/<KEY>`, `bugfix/<KEY>` или `hotfix/<KEY>`. `<KEY>` — ключ из трекера (`PROJ-123`). Без хвоста после номера.
3. Интеграция — через merge request / pull request в `dev` (или вашу базовую ветку).
4. Прямые коммиты в `dev` / `prod` / `main` запрещены (защитите ветки на сервере).

Какой префикс выбрать:

- `feature/` — новая работа по задаче, а также баг, найденный до релиза (в ветке фичи или в `feature/<ключ задачи-бага>`);
- `bugfix/` — исправление бага, который дошёл до прода;
- `hotfix/` — срочное исправление прода.

PanDev считает мерж `bugfix/` и `hotfix/` исправлением сбоя: он входит в долю сбоев (Change Failure Rate). Баг до релиза в `bugfix/` завысит её, хотя прод не падал.

Примеры:

- ✅ `feature/PROJ-42`
- ✅ `bugfix/PROJ-42`
- ❌ `feature/PROJ-42-login`
- ❌ `feature/login`
- ❌ `PROJ-42`

## Коммиты

Формат первой строки:

```text
feature/PROJ-42 - Краткое описание изменения
```

- Ключ — **тот же, что в имени ветки**: хуки отклоняют коммит с другим ключом. При мерже ключи из всех коммитов MR двигают задачи по статусам, и опечатка `PROJ-24` вместо `PROJ-42` сдвинула бы чужую задачу.
- Тип может отличаться от префикса ветки: `hotfix/PROJ-42 - …` в ветке `feature/PROJ-42` допустим.
- Допустимые типы: `feature`, `bugfix`, `hotfix`, `fix`, `refactor`, `docs`, `test`, `chore`, `ci`, `style`, `release`.
- Не проверяются: `Merge …`, `Revert …`, коммиты ботов обновления зависимостей. Для `fixup!` / `squash!` / `amend!` проверяется исходное сообщение после префикса.

## Почта автора

`git config user.email` — рабочая почта, та же, что в трекере и PanDev. Коммит с личной почтой не засчитывается никому, пока администратор не заведёт алиас.

## Merge requests

- Заголовок — в формате коммита: `feature/PROJ-42 - Описание`. При squash-мерже он становится сообщением коммита и должен пройти проверку.
- Целевая ветка: `dev` (или согласованная интеграционная).
- MR сразу ready for review; draft — только по явной договорённости.
- В `prod` / `main` — только из принятого потока окружений, не из feature-ветки напрямую (если у вас иначе — зафиксируйте явно).

## Люди и агенты

Правила одинаковы. Локальные хуки (`.githooks` или husky) и серверная проверка не дают запушить обход. Агенты читают `AGENTS.md` и `.cursor/rules/git-flow.mdc`.
